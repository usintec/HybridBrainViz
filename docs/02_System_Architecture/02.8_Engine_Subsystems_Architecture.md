# 1. Purpose

This document defines the internal organization of the HybridBrainViz Engine.

Rather than implementing functionality as a monolithic application, the engine
is decomposed into cohesive subsystems with clear responsibilities, explicit
interfaces, and well-defined dependencies.

The subsystem architecture promotes maintainability, extensibility,
testability, and long-term evolution into a reusable medical visualization
platform.

-------------------------------------------------------------------------------

# 2. Engine Philosophy

The HybridBrainViz Engine is built on the following principles:

- Single Responsibility
- Loose Coupling
- High Cohesion
- Dependency Inversion
- Interface-Driven Design
- Plugin-Oriented Extensibility
- Scientific Reproducibility
- Backend Independence

Subsystems expose services rather than concrete implementations.

-------------------------------------------------------------------------------

-------------------------------------------------------------------------------

# 4. Subsystem Design Principles

Each subsystem:

- owns a single functional area,
- exposes interfaces,
- hides implementation details,
- registers services through the Service Registry,
- publishes events,
- subscribes only to required events,
- is independently testable.

Subsystems communicate through contracts rather than direct implementation
references.

# 6. Communication Model

Subsystems communicate using:

- Service Registry
- Event Bus
- Commands
- Queries
- Domain Events
- Immutable Data Transfer Objects

Direct subsystem-to-subsystem coupling is discouraged.

-------------------------------------------------------------------------------

# 7. Dependency Rules

Allowed dependency direction:

```text
Applications
      │
      ▼
Subsystem Interfaces
      │
      ▼
Subsystem Implementations
      │
      ▼
Infrastructure
      │
      ▼
Platform
```

Subsystems depend on interfaces rather than concrete implementations.

-------------------------------------------------------------------------------

# 8. Lifecycle Management

Every subsystem follows a common lifecycle:

```text
Register

↓

Initialize

↓

Start

↓

Run

↓

Pause (optional)

↓

Resume (optional)

↓

Stop

↓

Shutdown

↓

Unload
```

The Engine Core coordinates subsystem lifecycle transitions.

-------------------------------------------------------------------------------

# 9. Service Registration

Subsystems register services with the global Service Registry during
initialization.

Services are resolved through dependency injection rather than direct object
construction.

Service registration supports multiple implementations of the same interface.

-------------------------------------------------------------------------------

# 10. Plugin Integration

Subsystems may be extended through plugins without recompiling the engine.

Examples:

- New AI segmentation models
- Alternative Marching Cubes implementations
- New rendering algorithms
- Additional evaluation metrics
- New medical image formats
- Alternative graphics backends

Plugins must implement published subsystem contracts.

-------------------------------------------------------------------------------

# 11. Thread Ownership

Thread responsibilities are separated by subsystem.

Typical threads include:

- UI Thread
- Workflow Thread Pool
- AI Inference Thread
- Asset Loading Thread
- Rendering Thread
- Background Tasks

Cross-thread communication occurs through message passing and immutable data.

-------------------------------------------------------------------------------

# 13. Architectural Summary

The HybridBrainViz Engine is organized as a collection of cohesive, loosely
coupled subsystems that collectively provide medical imaging, segmentation,
visualization, rendering, evaluation, workflow orchestration, and research
management capabilities. By separating responsibilities into independently
testable and extensible modules connected through interfaces, events, and
service registration, the architecture establishes a scalable foundation for
future research, clinical applications, and multi-platform deployment.
